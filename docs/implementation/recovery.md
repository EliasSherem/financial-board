# Recuperación de contraseña

Implementación aditiva en `server/recovery/`, React `/forgot-password` y `/reset-password`, y `auth.ts`. Conserva el hash bcrypt existente (coste 10), la identidad del usuario, finanzas y suscripciones. No se ejecutó ninguna migración de producción ni envío real de correo; las migraciones locales se probaron en MySQL aislado.

## Configuración y despliegue

1. Aplicar `database/migrations/003_recovery.sql` mediante el runner versionado antes de desplegar autenticación. Columnas nuevas `users.credential_kind` (`unknown/local/google`) y `token_version` (0 inicial). Tablas `password_reset_tokens`, `auth_rate_limits`, `auth_security_audit`, InnoDB y claves foráneas. No borrar estas columnas al revertir funciones.
2. Configurar `RECOVERY_ORIGIN=https://<dominio-propio>`, `RECOVERY_ALLOWED_ORIGINS` con el mismo origen HTTPS explícito, sin rutas, y `RECOVERY_RATE_SECRET` aleatorio de al menos 32 caracteres. `RECOVERY_TOKEN_TTL_MINUTES=30` opcional, rango admitido 5–60. No se usa Host, redirect del cliente ni `CLIENT_URL` sin validación. Configurar `RESEND_API_KEY` y `RESEND_FROM` de un dominio verificado por el operador. **No se ha comprobado la verificación del dominio.** Deshabilitar tracking de apertura/clics en Resend para estos correos; no hay trackers en los templates. El correo de ejemplo está en `recovery-email-preview.html`, con dominio `.invalid` y token falso.
3. Montar `recovery/routes.ts` en Express antes del router legado. Configurar la confianza de proxies únicamente según la topología verificada, para que `req.ip` represente la IP real y no un encabezado arbitrario. El límite por cuenta no depende de esa topología. Una configuración incompleta devuelve confirmación neutral en forgot y error 503 en reset; revisar logs saneados/configuración antes de habilitar el enlace públicamente.
4. La página web funciona sin app. Link enviado: `https://<origen>/reset-password#token=...`. GET no consume ni cambia nada. React captura el fragmento en memoria, lo elimina mediante replaceState antes del render, excluye AssistantChat y cualquier instrumentación en recuperación; `index.html` y Nginx añaden no-referrer. Sólo mientras Login está montado, su integración Google usa `strict-origin-when-cross-origin` antes de cargar/inicializar GIS, según la [configuración oficial de Google](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid). Al salir de Login restaura la política anterior, también al navegar por la SPA hacia recuperación; no se cambia la política global ni el header de `/reset-password`. No se almacena el token en localStorage, analytics, auditoría, errores ni logs. Botón opcional abre el scheme existente `financialboard://reset-password#token=...`; iOS/Android deben soportarlo. No se afirma asociación Universal/App Link HTTPS ni archivos de asociación desplegados. El cliente siempre puede concluir en web en otro dispositivo.
5. Ejecutar `cleanupRecoveryRecords()` desde mantenimiento diario: claves de rate limit tras 2 días sin actividad; tokens tras 30 días de vencidos; auditoría saneada tras 30 días. Eliminación de usuario borra tokens y anonimiza la referencia de auditoría.

## Proveniencia de credenciales legacy

El esquema previo almacenaba bcrypt tanto para contraseña elegida como para contraseña aleatoria Google; no conservaba proveedor. No existe una clasificación fiable a partir de email o hash. Migración marca existentes `unknown`. Signup nuevo marca `local`; nuevo usuario Google marca `google`. Login por contraseña correcto demuestra `local`; login Google en un usuario existente **no cambia** la clasificación porque puede estar enlazado a una cuenta local.

Para cuentas legacy que ya olvidaron la contraseña, el operador debe confirmar la proveniencia con sus registros y ejecutar explícitamente, desde entorno configurado correcto:

```sh
node --import tsx server/recovery/classify-credential.ts --user-id <id-real> --kind local --apply
```

También admite `--kind google`. Sólo cambia una cuenta real aún `unknown`, registra el evento y nunca cambia el hash. No se ejecutó este comando contra ninguna cuenta. Este dato externo es necesario para recuperar legacy desconocidas sin crear contraseñas en usuarios SSO por accidente. La respuesta anónima para local/no existente/SSO/unknown es idéntica; UI orienta a continuar con Google cuando sea el método utilizado.

## Contrato y garantías

- POST `/api/auth/forgot-password`: `{email,language:'es'|'en'}`. Siempre 200 con `{success:true,message:<neutral>,retry_after_seconds:60}` aunque correo no exista, SSO, input inválido, throttle o mailer no disponible. Mismo cuerpo, jitter/floor 700–900ms, consultas de límites compartidas. Correo se inicia después del commit sin esperar latencia de proveedor para responder; no se promete una igualdad matemática de tiempos cuando hay caídas/lentitud DB. Timeout de envío 10s. Una caída de proceso tras commit antes de entrega puede requerir reenvío: no persistimos copias recuperables del token.
- Límites DB persistentes por HMAC de IP: 20 solicitudes/hora; por cuenta normalizada: 5/hora y 60s entre intentos. Intentos repetidos cuentan, incluso inexistentes. No bloquean login. Reset: 20 intentos/hora/IP; cambio autenticado: 20/hora/cuenta. Se almacenan hashes HMAC con secret separado, nunca IP/email en tablas de límites. Revisar rate limits perimetrales además, sin sustituir estos límites.
- Token 32 bytes CSPRNG, base64url, sólo SHA-256 persistido. Una nueva solicitud aceptada invalida previas. Issuance y consumo bloquean primero usuario y luego token. Consumo, hash nuevo, invalidación restantes, incremento de versión y auditoría se confirman en una misma transacción. Vencimiento comprobado bajo lock contra UTC actual DB. Dos clientes no pueden consumir dos veces. No se envía nueva contraseña por correo.
- POST `/api/auth/reset-password`: `{token,password,confirm_password,language?}`. 200 `{success:true}`; 400 `PASSWORD_INVALID` o `INVALID_OR_EXPIRED_LINK` con `reason:invalid|expired|used`; 429 `RATE_LIMITED`; 503 `RECOVERY_UNAVAILABLE`. UI distingue inválido/vencido/usado y ofrece reenvío. No auto-login.
- Política nueva contraseña: al menos 6 caracteres (compatible con registro), máximo 72 bytes UTF-8 para evitar truncado silencioso bcrypt. Confirmación exacta, sin normalización de contraseña. Login/reauth conserva compatibilidad con contraseñas legacy más largas (hasta 1024 bytes); sólo nuevos hashes limitan a 72.
- POST `/api/auth/change-password`, Bearer + `{current_password,password,confirm_password,language?}`, exige bcrypt de contraseña actual, no admite cuenta Google, valida y cambia bajo lock. Perfil web ahora hace cambio real, limpia sesión y vuelve al login. Ediciones anteriores de nombre/email/preferencia local siguen siendo locales; no se introduce un endpoint de perfil ficticio.
- Tras commit, mail de aviso sin token. Todas las rutas protegidas comparan JWT `token_version` con DB en cada request. JWT legacy sin campo equivale a0, así conserva sesión hasta revocación. Reset incrementa versión y revoca acceso inmediato a nuevas requests en **todos** los dispositivos; operaciones ya iniciadas no pueden deshacerse retroactivamente. No hay refresh tokens paralelos. Siguiente login contraseña/Google emite versión actual. DB indisponible falla cerrado503; inexistente/expirado/revocado401.

## Rollback

Desactivar UI de recuperación o retirar router de forgot/reset si fuera necesario, manteniendo authenticateToken y token_version: volver al middleware antiguo resucitaría JWT revocados. Preservar passwords, versiones, tokens hash y auditoría. No reducir versiones ni restaurar hashes antiguos. La migración es aditiva; un rollback funcional no elimina las tablas. Restaurar un snapshot completo de DB sólo bajo procedimiento de incidente específico del operador.

La migración008 añade `users.email_normalized` generada (`LOWER(TRIM(email))`, VARCHAR100 STORED) e índice **no único**. La consulta de recuperación usa ese índice para evitar un escaneo con locks de toda la tabla. Si dos correos legacy se normalizan al mismo valor, la respuesta sigue neutral y no se emite enlace hasta reconciliación operativa. La prueba MySQL incluye este caso y verifica que EXPLAIN vea el índice.
